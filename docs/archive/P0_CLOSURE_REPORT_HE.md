# דוח סגירת P0 — Eden Zino Dance

**תאריך:** 17.07.2026  
**גרסה:** 1.2.0

## מסקנה

כל פערי P0 שניתן לסגור בקוד ללא חשבונות ספק אמיתיים נסגרו ונבדקו. המערכת כוללת כעת שער מוכנות לייצור שמונע תחושת מוכנות מזויפת: גם כאשר הקוד תקין, הממשק מציג חסימה עד שבוצעו בפועל עסקת PayMe והחזר PayMe בסביבה הפעילה, הוגדרו Turnstile ודוא״ל, הוזנו פרטי העסק ואושרו המסמכים המשפטיים.

אין אפשרות אמינה "לסגור בקוד" בדיקת מסוף PayMe חי או אישור משפטי. אלה פעולות חיצוניות, והמערכת דורשת הוכחה שלהן לפני Go-Live.

## P0-1 — PayMe ותהליך תשלום

- יצירת עסקת PayMe נעשית בשרת בלבד.
- המחיר והסכום נשלפים מהמסד ולא מהדפדפן.
- אישור הרשמה נעשה רק בעקבות Callback מאומת; עמוד החזרה אינו מאשר תשלום.
- נבדקים מזהה התשלום הפנימי, מזהה המוכר, סכום העסקה וסוד Callback.
- Callback כפול מטופל באופן אידמפוטנטי.
- כל Payment ו־Refund מסומנים ב־`provider_environment`; עסקת Sandbox אינה יכולה להיחשב כהוכחת ייצור.
- שער הייצור דורש לפחות עסקת PayMe מוצלחת אחת בסביבה הפעילה ומונע מוכנות כאשר ה־API עדיין מצביע ל־Sandbox.

**מה נשאר חיצוני:** הזנת מפתחות המסוף וביצוע בדיקות Sandbox/Production מול חשבון PayMe של העסק.

## P0-2 — החזרים

- נוסף מנגנון Refund Provider עבור PayMe עם נתיב ניתן להגדרה באמצעות `PAYME_REFUND_PATH`.
- החזר יכול להתחלק אטומית בין כמה תשלומים.
- נשמר סכום שהוחזר בכל תשלום.
- הקצאה כפולה של אותו סכום נחסמת.
- לכל החזר מפתח Idempotency קבוע לניסיונות חוזרים.
- קיימים מצבי `PROCESSING`, `SUCCEEDED`, `FAILED`, `MANUAL_ACTION_REQUIRED` ו־`CANCELLED`.
- קיימים Retry, השלמה ידנית מאומתת וביטול הקצאה לאחר בדיקה מול הספק.
- Callback של PayMe יכול להשלים החזר קיים.
- שער הייצור דורש החזר PayMe מוצלח אחד לפחות בסביבה הפעילה.

**הערת אמת:** פורמט Refund API עשוי להיות תלוי ביכולות ובהרשאות של מסוף PayMe. אין לעבור לייצור לפני בדיקת payload ותגובה מול המסוף שלך.

## P0-3 — הודעות וחשבוניות

- ספק חסר אינו נרשם עוד כ־`SENT`.
- חוסר הגדרה נרשם כ־`CONFIGURATION_ERROR`.
- נמען חסר נרשם כ־`SKIPPED`.
- כשל ספק נשמר ככשל ומופיע במסך התפעול.
- קיימים Retry ומספר ניסיונות מוגבל.
- Webhook דורש גם כתובת וגם סוד חתימה.

## P0-4 — אזור לקוח ועמודי סטטוס

- בוטל חיפוש לקוח לא מאובטח לפי דוא״ל/קוד בלבד.
- נוסף Magic Link חד־פעמי וקצר־חיים.
- נוסף Session לקוח ב־Cookie מסוג HttpOnly.
- גישה להרשמה ולהזמנה דורשת Session מתאים או Token ציבורי חתום.
- Token נשמר במסד כ־Hash ולא כטקסט גלוי.
- נוספו Logout ותפוגת Tokens/Sessions.

## P0-5 — אבטחת מנהלים ו־Rate Limiting

- נוספו Cloudflare Rate Limiting bindings נפרדים ל־Public ול־Authentication.
- Login, איפוס סיסמה ופעולות רגישות מוגבלים בקצב.
- נוספה נעילת חשבון לאחר חמישה ניסיונות שגויים למשך 15 דקות.
- נוסף איפוס סיסמה באמצעות Token חד־פעמי וקצר־חיים.
- כל Sessions המנהל מבוטלים לאחר שינוי סיסמה.
- נוסף OTP בדוא״ל לכניסת מנהלים; ברירת המחדל בייצור היא מופעלת.
- נוסף Cloudflare Turnstile בצד הלקוח ואימות Siteverify בצד השרת.
- שער הייצור חוסם כאשר Turnstile, MFA או Rate Limit bindings חסרים.

## P0-6 — ביטול הרשמה

- הביטול מתבצע באמצעות פונקציה אטומית במסד.
- מחושבת יתרת ההחזר המותרת.
- נפתחים החזרים מפוצלים לפי העסקאות ששולמו.
- קרדיט כרטיסייה או מנוי מוחזר כאשר הוא שימש להרשמה.
- ביטול חוזר אינו יוצר החזרים או הודעות כפולים.
- סטטוס נשאר `REFUND_PENDING` עד שכל ההחזרים הושלמו.
- לאחר שחרור המקום מתבצעת הזמנה מרשימת ההמתנה.
- נשלחות הודעות נפרדות לביטול הממתין להחזר ולביטול שהושלם.

## P0-7 — העברה בין סדנאות

- ההעברה נועלת את הרשמת המקור ואת סדנת היעד במסד.
- הקיבולת נבדקת בתוך אותה פעולה אטומית.
- העברה כפולה או תחרות על המקום האחרון נחסמות.
- העברה לסדנה במחיר שונה נחסמת במקום ליצור פער כספי שקט.
- נוסף ממשק ניהול לביצוע ההעברה.
- נשלחת הודעת העברה ונשמר Audit Log.

## P0-8 — מסמכים משפטיים ושער Go-Live

- שמירת מסמך יוצרת טיוטה ואינה מפרסמת אותו אוטומטית.
- שינוי במסמך מבטל אישור קודם.
- רק OWNER יכול לאשר מסמך.
- האישור דורש סימון מפורש והערת אישור.
- נשמרים המאשר, מועד האישור והגרסה.
- שער המוכנות דורש מסמכי TERMS, PRIVACY, CANCELLATION ו־ACCESSIBILITY מאושרים שאינם DRAFT.
- שער המוכנות דורש פרטי עסק מלאים.

**מה נשאר חיצוני:** עורך דין צריך לאשר את הנוסח בפועל. המערכת מתעדת את האישור אך אינה מהווה ייעוץ משפטי.

## תיקון תפריט המובייל

שורש התקלה היה Drawer מסוג Flex ש־Chrome אפשר לו להתכווץ למרות `position: fixed`.

בוצע:

- רוחב פיזי קבוע ביחס ל־viewport.
- `flex-shrink: 0` ו־`flex: 0 0 auto`.
- רוחב מינימלי ומקסימלי מפורשים.
- קישורים וכפתורים ברוחב מלא ללא כיווץ.
- גלילה אנכית בתוך התפריט.
- תמיכה ב־safe area.
- במסכים עד 380px התפריט נפתח ברוחב מלא.
- אותו תיקון הוחל גם על תפריט הניהול.
